1. DNS 泄露（实测证据）

① 53 端口劫持：dig @8.8.8.8 / @192.168.31.1 / @223.5.5.5 / @1.1.1.1 doubleclick.net
   → 四个全部返回空（说明查询都进了 sing-box 的 DNS 规则，而不是真的发到那些解析器）

② 出口回显：dig TXT o-o.myaddr.l.google.com
   → 系统解析器与 @1.1.1.1 都返回 172.64.212.11（Cloudflare 的解析出口）
   → 海外域名由 Cloudflare DoH 经代理解析，ISP 看不到

③ 明文 DNS：ss -un / -tn 里没有任何指向外部 :53 的套接字
   → 没有 UDP/53 明文外发（sing-box 走 DoH over 443）
   现存 53 监听者只有本机服务：127.0.0.53/54（systemd-resolved）、192.168.122.1（libvirt）

④ 国内解析：ss 显示到 223.5.5.5:443 的 DoH 连接
   → 国内域名走阿里 DoH（不是明文 UDP，比之前那版更强）

⑤ resolvectl：tun0 = 172.19.0.2 / fdfe:dcba:9876::2，DNS Domain ~.
   → 系统解析器 100% 指向隧道
   （**追注 2026-10-02 23:01：这是 TUN 模式下的状态，现已不适用**——当前 eBPF 模式没有 tun0，
   `resolvectl` 里 wlan0 用 `192.168.31.1` 与宿主路由器的 ULA 网关（`fd00:6868:…::1`），解析器不再指向隧道；
   劫持改由 eBPF 在 53 端口完成，实测 `dig @8.8.8.8 doubleclick.net`、`dig @223.5.5.5 doubleclick.net` 都立刻返回 NXDOMAIN，拦截仍有效。）

唯一残留面：dns.servers 里那个 dns-local（type: local）现在没人引用；一旦将来被误引用，就会绕过 DoH 走系统解析器 → 建议直接删掉。
（追注 2026-10-02 23:01：已删除——当前 dns.servers 共 7 条，无 dns-local。）

一个天然限制（你已规避）：hijack-dns 只覆盖 53 端口/dns 协议，浏览器自作主张的 DoH（443）不经过 sing-box 的 DNS 规则。
好在你的广告拦截同时写在 route.rules 里（连接层按 sniff 出的域名 reject），所以即使用户开浏览器 DoH，
广告连接照样被 RST —— 这个”双写”设计是对的，别只留 DNS 那一条。

5. 真要切到 eBPF，需要改什么

5.1 配置：tun-in → ebpf-in（mixed-in 保留）

{
  "type": "ebpf",
  "tag": "ebpf-in",
  "network": ["tcp", "udp"],
  "local": {
    "enabled": true,
    "data_plane": "cgroup",
    "dns_mode": "respect_policy",
    "bypass_private_address": true,
    "ipv6": true,
    "exclude_uid": [ "<可选：不需要走代理的 UID>" ]
  },
  "shared": { "enabled": false }
}

  • 端口 53：由 dns_mode 在内核侧接管（hijack 先接管再筛 UID，respect_policy 先筛再接管），
    替代 TUN 时代的 hijack-dns 路由动作；原规则留着无害，可删。

  • IPv6：由 local.ipv6 显式开关，不再需要为了 v6 去给 TUN 配地址，也不会再出现
    ip -6 rule 里那条 unreachable 黑洞（那是 TUN 模式的防泄露设计）。

  • 分应用（Linux 上 TUN 做不到的事）：include_uid / exclude_uid / *_uid_range；
    include_package / exclude_package 是 Android 专用，桌面别用。

  • 局域网 / 虚拟机共享：shared 填的是下游接口，不是上游！
    你这台机器上默认出口是 wlan0，所以不要填 wlan0；要让 libvirt 的虚拟机也走代理，应填 virbr0：

    "shared": { "enabled": true, "data_plane": "packet_rewrite", "interface": ["virbr0"] }

    且 shared 模式自己不做 NAT / DHCP / IPv6 RA（那些仍由 libvirt dnsmasq 负责），
    只支持以太网帧接口（raw-IP / PPP / 隧道链路要换 socket_assign）。

  • 一个实例只能有一个 ebpf 入站做 local 接管；绝对不要 TUN 与 eBPF 同时开（等于两个透明代理）。

7. Android（NetProxy 模块）怎么判断能不能用

  • 模块只提供 eBPF 透明代理入站，没有 TPROXY/REDIRECT 回退：内核能力不足 → 透明代理根本起不来。
  • 厂商内核可能关掉/回移部分 BPF 能力，不能只看 Android 或内核版本号，要用模块自带探测：
su -c '/data/adb/modules/netproxy/netproxyctl ebpf status configured'
su -c '/data/adb/modules/netproxy/netproxyctl ebpf status all --raw'
  • 默认数据面：本机 cgroup（EBPF_LOCAL_DATA_PLANE=cgroup），共享网络 packet_rewrite（EBPF_SHARED_ENABLED=0 默认关）。
  • 需要：Magisk / KernelSU / APatch + Root；内核支持 BPF、TC classifier、透明 socket、socket lookup；本机路径还要 veth 与策略路由（未复核：本机实测 tc 数据面在 7.2.8 上不可用、而 cgroup 路径不依赖 veth，这句是照模块文档转述的，没有实机验证）。
  • 它的”sing-box 配置”与你的 /etc/sing-box/config.json 不是一份东西：它用 runtime/ 现生成的 Provider + eBPF 配置，
    静态主配置在 config/singbox/config.json。你的 TUN 配置思路（规则集、DoH、selector）可以照搬，但 tun 入站整段要去掉。

📌 2026-10-02 晚追注（本节保留原文，属历史记录）：现行单元是 User=root（自建 sing-box-ebpf 包），
/var/lib/sing-box/cache.db 现为 root:root 644，所以”被改成 emo 属主导致服务写不了”这个具体故障
在当前单元下不会复现；但下面两条铁律（别拿线上配置跑非 root check、active ≠ 就绪）仍然成立。
⚠️ 另：本次没能复现”check 初始化 cache-file”这一步——把 cache_file.path 指到可写临时目录后
sing-box check exit=0 且没有生成文件；带 ebpf 入站时则更早地在 map create: operation not permitted
失败。所以”check 走到服务初始化”是真的（会去建 eBPF map），但”它顺手重建了 cache.db“这一环存疑。

症状：systemctl restart sing-box 后服务 active 一秒即挂，无限重启循环，tun0 消失：

FATAL[0000] start service: initialize cache-file: open /var/lib/sing-box/cache.db: permission denied

根因：/etc/sing-box/config.json 里 experimental.cache_file.path 是绝对路径
/var/lib/sing-box/cache.db，而非 root 身份跑 sing-box check -c/-C <线上配置> 也会真的初始化
cache-file（这个 fork 的 check 会走到服务初始化）。于是该文件被重建为 emo:emo 644，
而服务用户是 sing-box（目录 755，只有属主可写）→ 服务再也写不了自己的缓存。
当时老进程还握着旧 inode，所以表面无恙，直到重启才炸。

修复（一条命令，缓存可丢弃）：

sudo chown sing-box:sing-box /var/lib/sing-box/cache.db && sudo systemctl restart sing-box
# 或者干脆：sudo rm -f /var/lib/sing-box/cache.db && sudo systemctl restart sing-box

两条铁律：

  1. 不要用非 root 对线上配置跑 sing-box check / run。要验证就先复制一份，并把
    experimental.cache_file.path 改到 /tmp（试跑脚本 v2 已内置这个隔离）。
  2. systemctl 报 active ≠ TUN 已就绪：实测有 1 秒级竞态，is-active 为真时 tun0
    可能还没建出来。判断健康要 is-active + ip link show tun0 一起看（脚本 v2 已改成轮询 10s）。
    （eBPF 模式下没有 tun0，判据要换成 api ebpf 的附件状态 + “不设代理的出口 == 经代理的出口”，见 09 文档 §9。）

    逐条列出 PASS / FAIL / UNKNOWN。这是”改配置前先确认内核吃不吃得下”的按钮，
    它不挂载程序、不改动任何状态。要测虚拟机共享路径就在输入框填下游接口（例如 virbr0）。
  • 日志：journalctl -u sing-box 最近 200 行。
  • 集成卡片：Clash API 地址、密钥（一键复制），以及三个入口 ——
    zashboard（内嵌，深链 #/setup?...&secret=… 自动带密钥，点开即配好）、官方 dashboard（127.0.0.1:9091/dashboard/，讲 sing-box 原生 API，排障用）、
    MetaCubeXD（只在 sing-box 配置里启用 clash_api.external_ui 时才出现，见 §9）。

3.2 节点与订阅

  • 订阅：填 URL → 添加并拉取。支持
    • base64 编码的链接列表 / 纯链接列表：ss://（SIP002 与 legacy）、vmess://、vless://、
      trojan://、hysteria2:// / hy2://、tuic://
    • Clash YAML（proxies:）；装了 python-yaml 用它，没装则用内置子集解析器
    • 暂不支持的类型（如 snell）会被跳过并在提示里列出，不会污染配置
  • 写入配置：把启用订阅的节点写入 outbounds，并把它们加进托管策略组。
  • 策略组与节点：从 Clash API 实时读；点节点即切换，点「测」做单点延迟测试，「整组测速」批量测。
  • 订阅抓取默认走本机代理口（subscription_proxy，默认 http://127.0.0.1:7892），
    这样机场订阅在国内也能拉到；不需要就把它设成空串。

托管契约（很重要）：面板只碰自己上次写进去的东西——
managed.json 记录 outbound_tags（自己加的节点）与 group_members（自己往组里加的成员）。
重新写入时先删掉这些、再加新的，不会动你手工维护的节点和组成员（例如你的 Download 组、
地区组里的手写成员）。默认托管组是 Proxy（selector）与 Auto（urltest），可在面板配置里改。

3.3 分应用策略

  • 模式：关闭 / 黑名单（选中的不走代理）/ 白名单（只有选中的走代理）。
  • 应用列表来自 .desktop 条目 + /proc 扫描，按 UID 聚合（显示进程数与可执行文件）。
  • 也可以手工加 UID。点「应用策略」写回 eBPF 入站的 local.include_uid / exclude_uid，
    然后走安全管线重启核心。
  • Linux 上策略粒度就是 UID（同一 UID 的多个进程一起生效）；include_package 是 Android 专用字段，桌面不要用。

3.4 配置与服务

  • 配置编辑器：整份 config.json，可「仅校验」（sing-box check）或「应用并重启」。
  • 应用流程：JSON 解析 → sing-box check → 备份 → 原子替换 → systemctl restart → 健康检查
    （is-active，TUN 模式再等 tun0，可选再经代理口探一个 URL）→ 任何一步失败就写回旧配置并重启。
  • 备份与回滚：每次应用前自动备份到 /etc/sing-box/backups/（保留最近 backup_keep 份，默认 30），
    列表里可一键恢复。恢复本身也走同一条安全管线。

5. 安全模型

  • 只监听本机 + 令牌鉴权（secrets.compare_digest 常量时间比较）；令牌文件 0600。
  • 以 root 运行（systemd 单元里写明原因）：写 /etc/sing-box/、systemctl、以及
    sing-box check 遇到 eBPF 入站时会真的创建 BPF map（非 root 必然失败）。
  • 没有任意命令执行接口：只有固定的几类操作（服务控制、配置读写、订阅、策略、探针、日志）。
  • 静态目录做了路径穿越防护（必须是 ui_dir / zashboard_dir 的子路径）。
  • 写配置永远先校验、先备份，失败自动回滚——这条是本面板存在的主要理由。

DNS 层：发现规则顺序 bug 并已修复 🐛

原配置里 DNS 规则顺序是：apple@cn → cn → google/AI → !cn → 广告 reject。
广告 reject 排在最后，于是同时属于其他分类的广告域名会先被路由出去，照样解析成功：

广告域名 为什么漏
pagead.l.google.com 命中 geosite/google（第 3 条）→ 解析成 142.251.169.155
adwords.com 同上 → 172.217.221.113
guanggaoad.youku.com 命中 geosite/cn（第 2 条）→ 182.242.82.251

而路由规则里 reject 排在第 4 条（在 google/cn 之前），所以连接层拦得住 —— 两边不一致。

修复：把广告 reject 提到 DNS 规则第 1 条。现在顺序为
广告 reject → apple@cn → cn → google/AI → !cn，已通过 sing-box check（exit=0）。
修复后这类域名在 DNS 阶段直接 NXDOMAIN，浏览器不会再去尝试连接。

追注（2026-10-02 晚实测）：顺序与”第 1 条”仍然对，但动作已不是 reject：现配置第 1 条是
action: predefined + rcode: NXDOMAIN。原因：DNS 层的 reject 回的是 REFUSED，
systemd-resolved 收到上游 REFUSED 后不转告客户端而是去重试其他上游，应用会一直等到超时（约 5 秒）；
predefined+NXDOMAIN 是正常应答，应用立刻失败并做负缓存（详见 docs/09 §3）。
另外广告拦截的规则集已从 1 份扩到 5 份（geosite/category-ads-all + Ads_AWAvenue + anti-AD +
ads-extra + adblockfilters），DNS 规则与路由规则两边同步引用。
复测：dig +short doubleclick.net → 空；dig random-zzq.doubleclick.net → status: NXDOMAIN；
对照域名 github.com 正常解析；dig +tcp 同样被拦。

这是 sing-box 的有意设计（没有 v6 出口就别让 v6 偷偷绕出去），所以不会泄露；代价是 v6 目标一律不可达。

nmcli con mod <wifi-ssid> ipv6.method disabled && nmcli con up <wifi-ssid>

一、sing-box / 内核

1. ebpf 入站只存在于某个 fork，上游没有

上游 SagerNet 的 sing-box 没有 ebpf 入站（文档 404）：这个入站在 reF1nd/sing-box 分支里
（with_ebpf 构建标签，Linux/Android）。而那个 fork 0 个 release → 想要就得自己编。
判断依据不是”文档说有”，而是：拿一个带 ebpf 入站的配置去 check，上游二进制直接报
unknown inbound type: ebpf。

2. 内核数据面要逐条探测，不能互相推断（我在这里推断错过一次）

先看结论：官方文档写得很清楚 ——

这四条路径（local cgroup、local tc、shared packet_rewrite、shared socket_assign）
不是按内核版本递进的能力层级。厂商内核可能支持其中一条，却在另一条的对象加载或挂载阶段拒绝。

实测结果（root 权限，逐条单独探测）：local cgroup ✅ / local tc ❌ /
shared packet_rewrite ✅（PASS 33）/ shared socket_assign ✅（PASS 31）。
即本机只是 local tc 这一条不可用，两条 shared 都可用 —— 容器/虚拟机在 eBPF 下能被接管。

我犯的错：local tc 实测失败（register TC eBPF TCP listener: operation not supported）之后，
我推断“shared 也是 TC 路径，所以同样不可用”，甚至据此给脚本加了守卫把这个方案挡掉。
但事实上 —— shared 我从来没真跑过（脚本卡在”找不到 podman 网桥”就退出了），
而且按上面的文档，这个推断本身就不成立。

正确的做法（也是文档给的做法）：用要用的那条路径单独做只读探测，并且
用与服务相同的权限（普通用户跑会得到一堆 unknown，因为建不了 BPF map）：

sudo sing-box tools ebpf status --shared-data-plane socket_assign  --interface wlan0 --json
sudo sing-box tools ebpf status --shared-data-plane packet_rewrite --interface wlan0 --json
sudo sing-box tools ebpf status --local-data-plane  cgroup --json

result: passed 才是通过；inconclusive 表示无法判定（多半是权限），fail 才是真的缺能力。
最终判据仍是真实启动成功（探测不挂载 hook，也不证明能挂上去）。

📌 2026-10-02 晚追注（本节保留原文）：结论已复核为正确，四条数据面至今仍是
local cgroup ✅ / local tc ❌ / shared packet_rewrite ✅ / shared socket_assign ✅。
只补一处边界：上面那句”容器/虚拟机在 eBPF 下能被接管”要限定成桥接进来的——
VM 与桥接的容器可以，rootless podman（pasta）不行（见 §6）。

2b. register TC eBPF TCP listener: operation not supported 的语境

同一条错误出现在 local tc 上。文档说明 TCP listener 有两条路：内核能建
BPF_MAP_TYPE_SOCKMAP 时优先用它，否则回退到不引用 SOCKMAP 的 legacy 段、直接调
bpf_skc_lookup_tcp。且 shared socket_assign 需要的是 socket lookup/assignment helper
（bpf_skc_lookup_tcp / bpf_sk_lookup_udp / bpf_sk_assign / bpf_sk_release），
不需要 local TC 才要的那些（bpf_get_socket_uid、bpf_redirect、bpf_skb_store_bytes…）。
所以这两条路径的可用性必须分开看。

FATAL start service: start inbound/ebpf[ebpf-in]:
      register TC eBPF TCP listener: operation not supported

本机 7.2.8-1-cachyos-bore-lto。而 shared 的 data_plane = packet_rewrite 走的是同一条 TC 路径
→ 一起不可用。

📌 2026-10-02 晚追注：这半句推断已被实测推翻（原文保留）。 shared.packet_rewrite 在 virbr0 上
挂载成功并端到端跑通：api ebpf 显示 role=shared mechanism=tcx framing=ethernet，
直连与走代理两条路都通过（详见 §6）。local tc 失败不影响 shared；因此本节末尾那条
“非 passed 就先拦下来”的守卫，其前提不成立。

最有价值的教训在这里：预检 --mode local 报 preflight_passed（PASS 37 / FAIL 0 / UNKNOWN 0），
看起来”全都支持”；但换成 --mode all 立刻变成 inconclusive（pass 13 / warn 2 / unknown 36，
其中 required_issues 28）。也就是说：

预检全绿 ≠ 能用。local 模式只覆盖 cgroup 路径；只有实跑才知道 TC 行不行。

✅ 2026-10-02 晚复核：非 root 跑 sing-box tools ebpf status --mode all --json 仍得
result: inconclusive、pass 13 / warn 2 / fail 0 / unknown 36（required_issues 28），与原文数字完全一致；
所以这一条是权限造成的，不是内核能力不足。（上文 --mode local 的 preflight_passed / PASS 37 那次是 root 跑的，非 root 复现不出来。）

所以我给脚本加了守卫：要动 tc/shared 之前先跑 --mode all，非 passed 就先拦下来，
别白重启一轮（--force 可以强行试）。

3. DNS 广告拦截别用 reject：会卡 5 秒

  • sing-box 的 DNS action: reject 回的是 REFUSED；
  • systemd-resolved 收到上游 REFUSED 后不转告客户端（它认为”上游坏了”，去重试其他上游），
    → 客户端（应用）一直等到超时，约 5 秒；
  • 换成 action: predefined + rcode: NXDOMAIN 后是正常应答，应用立刻失败并做负缓存。
    实测：doubleclick.net 从”约 5 秒”变成 11 ms。

诊断口径也要注意：resolvectl query 会明说 server or network returned error: REFUSED —— 这是
识破”到底是超时还是被拒”的关键工具。

4. 域名规则优先于 IP 规则（所以有些”误判”其实是设计）

日志里看到 74.125.250.129:443（Google 的 IP）走 direct 然后 i/o timeout，很容易以为是 geoip 误判。
查下来：三份 CN 规则集都不含这个 IP，google.cn / gstatic.com 也都正确走 Proxy。
最可能的解释是某个 geosite/cn 里的域名解析到了 Google 的 IP —— 域名命中直连规则，IP 再”国外”也走直连。
这是设计如此，代价是那条连接超时。

5. 官方 geoip/cn 会偏旧，需要第三份独立来源

实测本地 sing-geoip-rule-set 的 geoip/cn 只有 8045 条，上游 MetaCubeX 已经是 9648 条
（多出 8.130.0.0/15 等段）→ 阿里云 IP 8.130.222.175 被误判成国外、走了代理。
补一份新表（外加 mihomo_yamls 的 cncidr，17958 条）之后正确直连。

教训：IP 归属是”数据问题”，不是”配置问题”；官方包更新慢，值得自己滚动。

6. rootless 容器（podman + pasta）抓不到 —— 但原因不是原来写的那样

修正（2026-10-02 晚）：原先这里写的是「pasta 不创建宿主 socket，所以 cgroup 钩子看不见」。
这句已被实测推翻：

$ ss -tnp | grep passt
ESTAB  [fd00:6868:6868::71b]:34344  [<remote-ip>]:443  users:(("passt.avx2",pid=157862,fd=155))

pasta（进程名是 passt.avx2，不是 pasta）确实创建宿主 socket：DNS 转发与 TCP 转发都走宿主 socket。
这也解释了为什么容器内 DNS 能被劫持、国内直连能正常 —— 「钩子看不见」这个解释不成立。

仍然成立的是现象与处置（2026-10-02 晚复测）：

容器网络 出口 结论
rootless 默认（pasta） http=000 失败；Clash API 里也没有这条连接 ❌ 境外走代理这条路不通
容器内国内直连 <home-ip> 电信 ✅ 正常
容器内广告 DNS NXDOMAIN ✅ 劫持生效
--network=host <proxy-exit-ip> ✅ 可行

✅ 2026-10-02 晚本机复测（轻量）：podman run 起一个 alpine（rootless 默认 pasta）——容器内
nc -w6 -z 104.26.13.205 443 → 失败（rc=1）；nslookup doubleclick.net → NXDOMAIN（劫持生效）；
对照域名 example.com 正常解析。同时宿主 ss -tnp 仍能看到 passt.avx2 的宿主 socket
（本次是 IPv4：192.168.31.29:58850 → <home-ip>:80）。结论与上表一致。

eBPF 的覆盖边界（修正后）：local 管本机；shared 管桥接进来的包（VM / 桥接的 rootful 容器，
实测直连与代理都通过）；pasta 属用户态转发 —— 既不是本机 socket 的常规路径，也不是桥上的包，
所以两条路都不覆盖它。具体卡在哪一环尚未确证。

一条待验线索：pasta 的宿主 socket 用的是宿主 ULA 私网源地址（fd00:6868:6868::71b），
所以值得临时关掉 bypass_private_address 再复测一次 —— 若这样就能通，根因就是
「私网地址绕过」的判定把 pasta 的流一起绕过了（而绕过的结果是走直连，境外自然被墙）。

📌 2026-10-02 晚补充证据：宿主 socket 的源地址也可能是宿主局域网 IPv4，不只是 ULA
（实测 192.168.31.29:58850 → <home-ip>:80 users:(("passt.avx2",…))），所以”源地址是私网”这条线索
对 v4/v6 都成立。根因仍未确证（没有实测关掉 bypass_private_address）。

处置不变：eBPF 模式下容器要么 --network=host（实测出口 = 代理出口 ✓），要么切回 TUN。

7. 切换/重启有 2–3 秒 DNS 空窗，而且缓存会骗过你的检查

旧模式拆掉、新模式还没挂上的那几秒，查询可能漏出去并被 systemd-resolved 缓存。
我第一次切 eBPF 就是被这个骗了：健康检查查 doubleclick.net 拿到缓存里的阳性答案，
判定”DNS 没生效”→ 自动回滚。实际 eBPF 是好的。

修法（都写进脚本了）：

  • 切换后 resolvectl flush-caches；
  • 检查用随机子域（<hex>.doubleclick.net）—— 任何缓存都命不中；
  • 同时问一个对照域名（必须能解析），否则”空结果”可能只是查询失败（假通过）。

8. 非 root 跑 sing-box check 会污染 cache.db 权限

配置里若写死了 experimental.cache_file.path = /var/lib/sing-box/cache.db，以普通用户跑 check
会创建一个属于该用户的 cache.db → 之后 root 的服务启动时：

FATAL start service: initialize cache-file: open /var/lib/sing-box/cache.db: permission denied

修法：脚本里 check 时把 cache_file.path 指到临时目录；出过事就 chown sing-box:sing-box。
（我这台机器上这个坑留下了 19 条 FATAL，全在 08:55 —— 修完之后再没出现。）

📌 2026-10-02 晚追注：现行单元是 User=root（自建 sing-box-ebpf 包），/var/lib/sing-box/cache.db
现为 root:root 644 —— 所以”被非 root check 改成 emo 属主后服务写不了”这个具体故障在当前单元下
不会复现。另外本次没能复现”check 会创建 cache.db”这一步：把 cache_file.path 指到可写临时目录后
跑 sing-box check，exit=0 且临时目录里没有生成任何文件（带 ebpf 入站时则在更早的
map create: operation not permitted 就失败了）——所以那一环的确切机制存疑，但”check 要隔离
cache_file.path“这条保守做法建议保留。

9. 健康判据必须跟着模式走

TUN 看 tun0 是否出现；eBPF 没有 tun0。eBPF 最硬的判据是：

不设任何代理的请求，出口必须等于经本地代理口的出口。

这一条同时证明”内核接管生效”。辅助判据是 sing-box api ebpf（密钥与 clash_api.secret 相同）：

{ "inbounds": [ { "tag": "ebpf-in", "state": "normal",
    "localEnabled": true,  "localDataPlane": "cgroup",
    "sharedEnabled": true, "sharedDataPlane": "packet_rewrite",
    "attachments": [
      { "role": "local",  "mechanism": "cgroup", "interfaceName": "/sys/fs/cgroup" },
      { "role": "shared", "mechanism": "tcx", "interfaceName": "virbr0", "framing": "ethernet" } ] } ],
  "kernelRuntime": { "programs": [ { "name": "sb_ebpf_conn4", "type": "CGroupSockAddr" },
                                  { "name": "sb_share_in",  "type": "SchedCLS" },
                                  { "name": "sb_share_out", "type": "SchedCLS" } ] } }

（上为 2026-10-02 晚实测的精简结果：local 与 shared 两个附件都在，共用 11 个 kernel program。）

10. 规则集是”按需加载”的，内存数字要等热了再看

刚重启时量到 74 MB，跑一会儿变成 150 MB —— 不是泄漏，是规则集（尤其 anti-AD 那份 770 KB 二进制）
加载进内存。教训：比较内存要在同一”热度”下比。

📌 2026-10-02 晚复核：运行约 1 小时 20 分时 systemctl show -p MemoryCurrent ≈ 101–105 MB、
ps -o rss ≈ 118 MB。量级与”热度”规律相符，但绝对值随规则集版本与运行时长变，别拿固定数字当判据。

二、工具链

11. fs.protected_regular=1：脚本里别写死 /tmp/<固定名>

内核这个开关的意思是：在 sticky 的世界可写目录里，即使 root 也不能写属于别人的已存在文件（防符号链接攻击）。
我干跑时留下了一个 emo 属主的 /tmp/xxx.json，之后 root 跑脚本就 EACCES：

PermissionError: [Errno 13] Permission denied: '/tmp/sing-box-audit-new.json'

修法：一律 mktemp -d / tempfile.mkstemp。这一条同时咬到了脚本、面板后端、试跑套件三个地方 ——
凡是”普通用户也可能先创建同名文件”的路径，都是隐患。

12. 丢掉 dig 的 stderr，会把”超时”看成”拦截”

我早期所有”DNS 拦截 ✅”的判定，用的是 dig +short <域名> 无输出，而我把 stderr 丢进了 /dev/null。
问题是：被 reject（REFUSED） 和 超时 在 stdout 上都是空。带完整输出复测才发现真实语义是 REFUSED。

教训：判定”被拦截”时，必须区分”拿到否定应答”和”什么都没拿到”。

13. re.sub 的替换串会自己处理反斜杠

re.sub(pat, "printf 'x\\n'", text)   # ✗ 写进文件的是真实换行
re.sub(pat, lambda m: "printf 'x\\n'", text)  # ✓ 用函数当替换器

正则引擎会把替换串里的 \n 转成真实换行。我在这上面栽了两次（还以为是 shell heredoc 的锅）。
教训：re.sub 的替换串里出现反斜杠，就用 lambda。

14. 自提权要换算绝对路径（sudo 的 secure_path）

脚本里写 exec sudo -- "$0" "$@"，当用户在 shell 里敲的是裸命令名时 $0 就是裸名，
而 sudo 默认用 secure_path（/usr/local/sbin:/usr/local/bin:/usr/sbin:/usr/bin:/sbin:/bin）——
里面没有 ~/.local/bin → sudo 那一层报”找不到命令”。

修法：

self="$0"
[[ $self == */* ]] || self="$(command -v -- "$self")"
exec sudo -- "$self" "$@"

15. 杂项（每个都咬过一次）

  • makepkg 不接受子目录里的本地 source：UI 文件要摊平到包目录根。
  • install -D 多源语义奇怪：目标存在时用普通 install -m 更稳。
  • namcap 要求 LicenseRef-* 有对应许可证文件：/usr/share/licenses/<pkg>/ 下得放一份。
  • namcap 的”依赖可能不需要”是误报：它看不出运行期会 exec 那个命令。
  • 验证 TUI 要用 tmux capture-pane：伪终端尺寸是 0×0 时 TUI 根本不渲染（script 里先 stty rows/cols 或直接用 tmux）。
  • 内置动作不允许构建出空 argv：那是防”忘写 base_argv 导致光跑 pacman 打印用法”的策略测试，
    合法无参要显式 allow_empty = true。

三、测量方法（我在这里犯过错，所以单独一节）

  1. 结论方向对 ≠ 机制对。我把 REFUSED 当成”拦截成功”，方向没错（应用确实拿不到解析），
    但机制错（不是”安静地拒绝”，而是”卡 5 秒”）。如果不深挖，就永远不知道体验代价。
  2. 要留下”能证伪”的判据。比如”eBPF 生效”用「不设代理出口 == 代理出口」——任何一方不成立就会红；
    而”服务 active”这种判据什么都证明不了。
  3. 警惕缓存：DNS 缓存、resolved 缓存、订阅缓存都会让”刚才明明改好了”变成假象。用随机化输入破缓存。
  4. 对照必不可少：验证广告拦截要同时问一个”必须能解析”的域名；
    验证分流要同时问国内与国外各一个；验证”节点死”要换更长的超时再下结论。
  5. 分清”历史噪声”与”当前问题”：日志里 58 行告警，全在 12:23 之前；当前进程 0 行。
    只看总数会误判成”一直有问题”。

四、流程

  • 改配置的脚本一律走同一条管线：check → 时间戳备份 → 原子替换 → 重启 → 健康检查 → 失败自动回滚。
    这台机器上它已经自动救过一次（tc 数据面试错）。
  • 备份要带语义：config.<时间戳>.pre-ebpf.json / pre-dataplane.json / pre-tun.json ——
    出问题时一眼知道回到哪个状态。
  • 把”手工验证步骤”固化成脚本：我手工跑了十几轮同样的检查，后来写成了 sing-box-status
    （一屏出结果），再后来集成进 TUI 当动作。验证脚本化之后，每次改动都敢动了。

5) debug 日志          → 只有前三步都指向 sing-box 时才有必要开

才把范围从”shared 有问题”翻转到”客户端根本没发包”。

我踩的四个坑（全是”测试工具破绽伪装成被测对象问题”）

  1. netns 里 127.0.0.53 是它自己的 loopback → 宿主 resolved 不可达，DNS 全挂。
    修：给 netns 单独写 /etc/netns/<ns>/resolv.conf。
  2. netns 只配 IPv4，双栈域名会先试 IPv6 → ENETUNREACH，看起来像”境外连不通”。
    修：探测时强制 curl -4 并打印 curl -6 对照。
  3. 双重接管（最难查、也最重要）：netns 里的客户端是宿主上的一个进程，
    它的 socket 仍在宿主 cgroup 里 → 同时被 local cgroup 钩子和 shared 钩子看到。
    开着 local.bypass_rule_set 时，国内目标绕过 local（所以能从 shared 正常出去），
    境外目标被 local 先截走 → 那条路径失败 → 表现出来就是”shared 直连能通、走代理不通“。
    → 要验证 shared，必须临时只启用 shared（local.enabled=false），或直接用真实 VM。
  4. 抓包没 flush 就读文件 → 分析出来是空的（分析前必须先停掉 tcpdump）。

顺带发现的一个 fork 校验细节

local.enabled=false 时不能再留着 local.data_plane，否则启动直接失败：

FATAL create service: initialize inbound[1]: local.data_plane requires local interception

必须精简成 "local": { "enabled": false }。并且：改完配置必须先 sing-box check 再重启 ——
我的测试脚本当时没 check 就重启，把服务弄停了约 20 秒（已修）。这条对所有运维脚本都成立。

一条值得上报上游的边角情况

宿主上的进程如果源地址是 veth/网桥地址（即进程在 netns 里，而流量经 virbr0），
开着 local 钩子时它的境外连接会被 local 路径截走并以 ECONNREFUSED 失败（1 ms、零报文、token 地址显示为 127.0.0.1）。
真实 VM 的流量不是宿主进程，不受影响；这是很窄的场景，但记录下来。

  • 换掉：代理节点的 server → <node-server>、server_port → 0、password/uuid/sni/host
    → 占位符；两处 secret（clash_api 与 services[api]）→ <clash-api-secret>
    （两处在线上是各自独立的 43 字符随机值，快照里共用一个占位符）；
  • 没有换掉：DNS 的公共 DoH 端点（1.1.1.1 / 8.8.8.8 / dns.alidns.com / doh.pub）——
    那是公共设施，也是配置里最重要的思路之一。

生成脚本是「结构化脱敏」而不是「按键名替换」：server 这个键名同时出现在代理节点（要脱）
和 DNS 服务器（不该脱）里，按键名替换会把两者一起打掉。生成后有自检断言。

⚠️ 2026-10-08 修掉一个真实缺陷（W2）：dns.rules[*].server 里放的是 DNS 服务器 tag
（dns-direct / dns-proxy），而旧脚本只在「带 type 字段的 dns.servers[*]」里认 DNS 上下文，
dns.rules 条目没有 type → 它的 server 被当成节点主机名，统统替换成 <node-server>，
于是公开快照里 DNS 分流引用失真（是错误，不是泄漏）。修法：新增
is_dns_rule()（同时含 action、且 server 是字符串 → 视为 DNS 规则），并把递归上下文改为
context in {"dns", "dns_server"} or is_dns_server(obj) or is_dns_rule(obj)，遇到 dns /
default_domain_resolver 键把子树上下文标成 DNS；另加两条拒写断言：逐条比对源与输出的
dns.rules[*].server（不一致直接退出），以及 dns 段里出现 <node-server> 也退出。
本次快照已按真实 tag 还原：must-direct/apple@cn/cn+lyc/cn → dns-direct；
google+category-ai-!cn、geolocation-!cn+lyc/geolocation-!cn → dns-proxy。

switch-to-ebpf.sh 的开关

sudo ./switch-to-ebpf.sh   --data-plane cgroup        # local 数据面（cgroup 可用；tc 在本机必失败，见文末）
  --shared virbr0            # 开共享接管（VM/桥接容器）；--no-shared 关闭
  --shared-plane packet_rewrite   # 共享数据面：packet_rewrite（默认）或 socket_assign
  --bypass-cn                # 让命中 CN IP 的流量绕过 eBPF（省 CPU，DNS 仍劫持）
  --no-bypass-cn             # 撤销上面这个
  --force                    # 越过预检守卫（别用来白试 tc）

--bypass-cn 只影响 local；它与 shared.bypass_rule_set 互相独立。

test-shared-interception.sh 的开关

sudo ./test-shared-interception.sh              # 默认：与当前配置一致的条件下测试
sudo ./test-shared-interception.sh --shared-only # ★ 验证 shared 请用这个
sudo ./test-shared-interception.sh --debug-log   # 临时开 debug 日志，跑完自动还原
sudo ./test-shared-interception.sh --keep        # 出问题保留 netns 现场

为什么验证 shared 一定要 --shared-only：脚本里的”下游客户端”是 netns 里的一个宿主进程，
它的 socket 仍在宿主 cgroup 里 → 开着 local 时会被 local 钩子先截走，于是表现得像
“shared 直连能通、走代理不通”（其实两条钩子都插了一脚）。临时关掉 local 后只剩 shared 钩子，
才等价于真实 VM/下游的路径 —— 这时实测直连与代理都通过。

apply-audit-fixes.sh 的开关

sudo ./apply-audit-fixes.sh \
  --with-extra-ads       # 补 3 个国内广告端点（精确域名，不动 apex）
  --with-cncidr          # 加 mihomo 国内 IP 表（第三份来源）
  --with-direct-list     # STUN / 游戏主机 / LAN cache / NCSI 强制直连
  --with-dns-groups      # 把闲置的备用 DNS 编成故障转移组（fork 支持 type=group）
  --use-package-paths    # 规则集改指 /usr/share/sing-box-rule-sets（随 pacman 更新）
  --nxdomain-ads         # DNS 广告拦截从 reject(REFUSED) 改成 predefined(NXDOMAIN)
  --with-abf             # 接入 217heidai/adblockfilters（215k 条后缀，与 anti-AD 只重叠 35%）

不带开关 = 只做基础修复（补广告表 + 刷新 geoip/cn + 清理冗余规则）。

--use-package-paths 只认它内置的 tag 表（anti-AD / geoip/cn-fresh / cncidr-mihomo /
must-direct / ads-extra / adblockfilters）。表里漏掉的 tag 会被留在 /etc/sing-box/rule-set/，
于是 pacman -Syu 更新规则集包时它不会跟着更新 —— adblockfilters 就这么漏过一次，已修。

健康判据（两种模式不一样）

模式 判据
TUN tun0 出现 + 不设代理的出口 == 经本地代理口的出口 + 国内直连 + DNS 广告被拦
eBPF 没有 tun0，所以只看：sing-box api ebpf 有活动入站 + 不设代理的出口 == 代理出口 + 国内直连 + DNS 广告被拦

DNS 那项一律用随机子域（<hex>.doubleclick.net）并问一个对照域名 ——
否则 systemd-resolved 的缓存会把”没生效”伪造成”生效”（我第一次切 eBPF 就是这么被骗着回滚的）。

注意

sing-box-why 是怎么工作的（值得记）

  • 没被拦的域名：连一次真实连接，从 Clash API 读实际命中的 rule / rulePayload / chains —— 这是权威结果，不是猜的。

  • 被 DNS 拦下的域名：不会产生连接记录，所以退一步逐个规则集判定命中哪一个；AdGuard 来源的 .srs 无法反编译，会**如实标注”无法判定”**而不是硬猜。

  • 抽样踩到的坑：直连时 metadata.host 常为空、dig 默认只查 A 而系统可能走 IPv6、
    sniff 到的可能是 CNAME 目标（www.baidu.com → www.a.shifen.com）。
    所以最后是先解析、再连指定 IP、但保留 SNI —— 目的 IP 确定、分流仍按原域名判。

  • 这套脚本在 emoeem/toolbox-hub 里也有一份
    （多了注解头与自提权前导，用来当 TUI 动作）。两边的业务逻辑应当保持一致，改的时候一起改。

  • switch-to-ebpf.sh --data-plane tc 在本机一定会失败：内核不支持 local 的 tc 数据面
    （register TC eBPF TCP listener: operation not supported）。脚本会在 --mode all 预检不通过时
    提前拦住，别加 --force 白试。

  • 别把这条推广到 shared：共享数据面走的是另一套（TCX），本机实测可用
    （api ebpf 里能看到 role=shared mechanism=tcx），直连与代理两条路都通过。早期文档把两者
    混为一谈过，已修。

历史记录与当前结论分开阅读。 上游 trial/README.md 保留了 2026-10-02 早期试跑时的判断：“TC 数据面与 shared 都不可用”，当时因此倾向回到 TUN。这是当时的记录，不是当前结论。后续 root 级逐条探测已修正该判断：本机 local 的 TC 数据面不可用；shared 的 packet_rewrite / TCX 实测可用，桥接 VM 流量可以接管。本文保留历史经过和原有永久链接，当前结论以 01 审计报告、09 踩坑与经验 和 2026-10-08 完整审计报告 为准。

这一包东西用来回答最后一个问题：换成 eBPF 后，你那套已经审计过的行为还在不在。

怎么用

cd <本仓库>/trial
sudo ./run-ebpf-trial.sh                     # 只接管本机流量
sudo SHARED_IFACE=virbr0 ./run-ebpf-trial.sh # 顺带接管 libvirt 虚拟机

脚本做的事（只停/起服务，不改任何配置文件和开机项）：

  1. 从 /etc/sing-box/config.json 现生成试跑配置到 /tmp：删掉 tun-in、加上 ebpf-in
    （local: cgroup + dns_mode: hijack + bypass_private_address + ipv6；给了 SHARED_IFACE 才开 shared）。
  2. 用 root 跑 sing-box check（eBPF 入站的 check 会真的建 map，非 root 必定失败，这是权限不是配置）。
  3. 在 TUN 模式下先打一遍分（基线）。
  4. systemctl stop sing-box → 前台起 eBPF 核心（日志 /tmp/sing-box-ebpf-trial.log）→ 等 sing-box started.
  5. 同一套判据再打一遍分，并 diff 两轮结果。
  6. 无论成功、失败、Ctrl-C，退出时都会把系统 sing-box（TUN）拉回来。

打分判据（沿用 singbox-network-audit.md）

判据 期望
direct_isp_ip 你的电信 IP（国内直连）
proxy_exit_ip 代理节点出口 IP
ipv6_http_code 200（eBPF 下由 local.ipv6 接管）
ipv6_blackhole 0（不该再有 unreachable 黑洞规则）
ads_dns_answer 空（DNS 层广告拦截仍生效）
resolve_github ok
tun0_state eBPF 模式下应为 absent（不再有 TUN 设备）

结果落在 /tmp/sing-box-ebpf-trial-result.<时间戳>.txt。

试跑过了之后再谈什么

  • 要长期用 → 先打包（~/pkgbuild-source 加 packages/sing-box-ebpf/），再改 systemd 单元
    （补 CAP_BPF CAP_PERFMON，或直接 root 跑；见报告 §5.2），并保留 pacman 级回滚（pacman -S sing-box）。
  • 只是尝鲜 → 跑一次看完 diff 就结束，什么都不用改。

v2 修复（第一次试跑踩的坑，已解决）

第一次试跑暴露出脚本自身两个问题，与 sing-box/你的配置无关：

  1. -D /var/lib/sing-box 与服务共用 cache.db：试跑的 cache_file.path 指向服务自己的缓存文件；
    而该文件此前被非 root 的 sing-box check（我为了验证配置跑的）重建过，属主变成了 emo:emo。
    服务用户是 sing-box → 重新启动时 FATAL: initialize cache-file: permission denied → 崩溃重启循环。
    v2 已改为独立状态目录 /tmp/sing-box-ebpf-trial-state 与独立 cache.db，并在开跑前自动纠正线上 cache.db 属主。

    如果你在别的场合也踩到这个（服务起不来说 permission denied），一条命令修：

    sudo chown sing-box:sing-box /var/lib/sing-box/cache.db && sudo systemctl restart sing-box

    （cache.db 只是缓存，直接 sudo rm -f 掉也会自动重建。）

  2. 恢复逻辑太急：systemctl start 后只等 2s 就判定失败，撞上 RestartSec=10s 的重启退避窗口。
    v2 改为：先等端口 7892 释放 → systemctl restart → 轮询 is-active 最多 30s → 再验 tun0 是否回来。

另外打分函数也修了：广告 DNS 判据改为 dig @1.1.1.1（绕开 systemd-resolved 自己的缓存），
并在每轮打分前 resolvectl flush-caches——否则切换模式后可能读到上一轮的缓存答案，得出错误结论。

注意

  • 试跑期间只有一个透明代理在跑（脚本先停旧的），不会两个同时开。
  • 若 eBPF 核心起不来，脚本会打印日志尾部并立即恢复——网络最多中断几秒。
  • 别把 local.cgroup_path 写成你终端所在的 scope（预检里那条 kitty-…scope 只是探测进程自己的位置）；
    留空 = 挂 cgroup v2 根层级 = 全局接管。
