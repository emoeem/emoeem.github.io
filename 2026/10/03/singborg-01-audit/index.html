1. DNS 泄露（实测证据）

① 53 端口劫持：dig @8.8.8.8 / @192.168.31.1 / @223.5.5.5 / @1.1.1.1 doubleclick.net
   → 四个全部返回空（说明查询都进了 sing-box 的 DNS 规则，而不是真的发到那些解析器）

② 出口回显：dig TXT o-o.myaddr.l.google.com
   → 系统解析器与 @1.1.1.1 都返回 172.64.212.11（Cloudflare 的解析出口）
   → 海外域名由 Cloudflare DoH 经代理解析，ISP 看不到

③ 明文 DNS：ss -un / -tn 里没有任何指向外部 :53 的套接字
   → 没有 UDP/53 明文外发（sing-box 走 DoH over 443）
   现存 53 监听者只有本机服务：127.0.0.53/54（systemd-resolved）、192.168.122.1（libvirt）

④ 国内解析：ss 显示到 223.5.5.5:443 的 DoH 连接
   → 国内域名走阿里 DoH（不是明文 UDP，比之前那版更强）

⑤ resolvectl：tun0 = 172.19.0.2 / fdfe:dcba:9876::2，DNS Domain ~.
   → 系统解析器 100% 指向隧道
   （**追注 2026-10-02 23:01：这是 TUN 模式下的状态，现已不适用**——当前 eBPF 模式没有 tun0，
   `resolvectl` 里 wlan0 用 `192.168.31.1` 与宿主路由器的 ULA 网关（`fd00:6868:…::1`），解析器不再指向隧道；
   劫持改由 eBPF 在 53 端口完成，实测 `dig @8.8.8.8 doubleclick.net`、`dig @223.5.5.5 doubleclick.net` 都立刻返回 NXDOMAIN，拦截仍有效。）

唯一残留面：dns.servers 里那个 dns-local（type: local）现在没人引用；一旦将来被误引用，就会绕过 DoH 走系统解析器 → 建议直接删掉。
（追注 2026-10-02 23:01：已删除——当前 dns.servers 共 7 条，无 dns-local。）

一个天然限制（你已规避）：hijack-dns 只覆盖 53 端口/dns 协议，浏览器自作主张的 DoH（443）不经过 sing-box 的 DNS 规则。
好在你的广告拦截同时写在 route.rules 里（连接层按 sniff 出的域名 reject），所以即使用户开浏览器 DoH，
广告连接照样被 RST —— 这个”双写”设计是对的，别只留 DNS 那一条。

  • 本节的前提是错的：当时以为”本机内核不支持 TC 路径”，实际只有 local 的 tc 模式不可用，
    两条 shared 数据面实测都可用（§11，shared=packet_rewrite 以 TCX 挂在 virbr0 上）；
  • “pasta 不创建宿主 socket”这个机制解释也是错的（ss -tnp 可见 passt.avx2 的 ESTAB 宿主 socket，真正卡点未确证，见 §11.0 追注与 docs/09 §6）；
  • 因此当天夜间又切回了 eBPF：当前 inbounds[0].type="ebpf"，local.data_plane=cgroup + shared.data_plane=packet_rewrite（interface:["virbr0"]）。
    所以下表把 eBPF 写成”只有 local cgroup 一个数据面”已不符合现状（当前是 cgroup + shared 两个）；scripts/switch-to-tun.sh 保留作回退手段。

§11 一度被读成”本机内核不支持 TC 路径”，据此推断 eBPF 的 local cgroup 数据面覆盖不到 rootless 容器
（当时以为是”pasta 不创建宿主 socket”）。这两个前提现已被推翻（见上追注），
而 TUN 靠 auto_route 覆盖转发流量，容器/虚拟机天然被代理。
权衡”eBPF 的新特性”（分应用 UID 策略）与”容器+VM 的完整覆盖”后，当时选择回到 TUN：

能力 TUN eBPF (cgroup)
本机流量接管 ✅ ✅
容器（rootless pasta） ✅ auto_route 覆盖（本次未复测） ❌ 看不到（除非 --network=host；2026-10-02 晚复测仍是境外失败、国内正常）
虚拟机 / 共享网络 ✅ ✅ 实测通过（用 shared=packet_rewrite，不是 local 的 tc 模式；见 docs/09 §6）
分应用 UID 策略（面板） ❌ ✅
内核依赖 需 TUN 设备 需 BPF/cgroup（本机满足）

切换工具：scripts/switch-to-tun.sh（只替换 inbound，保留 DNS 故障转移组、predefined/NXDOMAIN
广告规则、15 份规则集与包路径；check → 备份 → 替换 → 重启 → 健康检查 → 失败自动回滚）。
干跑已验证：生成的配置 check 通过、7 个 DNS 服务器 / 15 份规则集 / 11 条路由规则全部保留。
（追注 2026-10-02 23:01：这两行的”14 份”当时是对的，现已改成实测的 15 份；7 个 DNS 服务器、11 条路由规则两项实测一致。）

备份链完整：config.*.pre-ebpf.json（TUN 定义来源）、config.*.pre-dataplane.json、
config.*.pre-tun.json（切回 TUN 时自动生成），任何一步都能回退。

追注（2026-10-02 23:01 实测）：/etc/sing-box/backups/ 里现有 pre-audit（8 个）、pre-ebpf（2 个）、pre-dataplane（3 个），
没有 config.*.pre-tun.json（最新一个是 config.20261002-214131.pre-audit.json，21:41）。
也就是说”切回 TUN”那一步要么没走这个脚本、要么没留下这个备份，”备份链完整”这句只对前两类成立。
